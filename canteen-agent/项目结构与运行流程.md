# 食堂品控智能 Agent 系统 — 项目结构与运行流程分析

> 本文档基于 `canteen-agent/` 目录的**真实代码**梳理，而非仅依据 README。
> 代码当前处于 **v3.0 → v4.0 的演进过渡期**：既有活跃运行的 v4.0 链路（ReAct + 工具 + 记忆 + 幻觉防护），也保留着 v3.0 已实现但**未接线**的 Supervisor 多智能体 / 信号融合 / 置信度评估 / 五库检索，以及一套旧版内嵌 Agent 的**死代码**。

---

## 1. 项目总览

一个基于 **LangGraph + Milvus + LLM** 的菜品质量智能分析平台：自动聚合顾客评价 → 情感/实体分析 → 生成 AI 整改方案 → 向量库沉淀品控经验 → 效果追踪后自动「飞升」金标，形成自进化闭环。

### 1.1 技术栈

| 层次 | 技术 |
|------|------|
| 前端 | Vue 3 + Element Plus + ECharts + Pinia + Vue Router + Vite（端口 3000） |
| 主后端 | FastAPI + SQLAlchemy(async) + Celery + APScheduler（端口 8000） |
| Agent 微服务 | FastAPI + LangGraph + LangChain + pymilvus（端口 8001） |
| LLM | OpenAI 兼容接口（`langchain_openai.ChatOpenAI`），默认 `gpt-4o` |
| Embedding | OpenAI 兼容接口，默认 `text-embedding-3-small`（1024 维） |
| 消息队列 | RabbitMQ（Celery broker）+ Redis（任务队列 / Celery backend） |
| 业务数据库 | MySQL 8.0（库名 `canteen_agent`） |
| 向量库 | Milvus 2.4+（**5 个 Collection**：gold / standard / sop / pattern / cycle） |

> 注意：README 与设计文档里写的 LLM 是「阿里云 DashScope qwen-plus」，但**代码默认配置已改为 OpenAI 兼容接口**（`gpt-4o` / `text-embedding-3-small`）。实际以 `.env` 配置为准。

### 1.2 部署拓扑

```
┌──────────────┐      ┌───────────────┐      ┌────────────────┐
│  Frontend     │─────▶│  Backend       │─────▶│  Agent 微服务    │
│  Vue :3000    │      │  FastAPI :8000 │      │  FastAPI :8001  │
└──────────────┘      └───┬───┬───┬───┘      └───┬────────────┘
                          │   │   │              │
                 ┌────────▼┐ ┌▼─────────┐  ┌────▼─────┐
                 │ RabbitMQ│ │ Redis    │  │  Milvus  │
                 │ (Celery)│ │ (队列)   │  │ (向量库) │
                 └────────┘ └──────────┘  └──────────┘
                          │
                 ┌────────▼────────┐
                 │  MySQL (业务数据) │
                 └─────────────────┘
```

- Backend 通过 HTTP 内部地址 `AGENT_INTERNAL_URL`（默认 `http://agent:8001`）调用 Agent 微服务。
- Celery Worker 独立进程，消费 Redis 队列里的菜品批次任务，逐个 POST 到 Agent。
- 多源评价数据（美团 / 微信 / POS / CSV）经 Backend 的 ETL 层统一入库。

## 3. 数据模型（MySQL）

| 表 | 用途 | 关键字段 |
|----|------|----------|
| `dishes` | 菜品主数据 | name, category, unit_cost, price, is_active |
| `reviews` | 用户评价（多源去重） | source, external_id(去重键), raw_text, sentiment, rating, dish_id, dish_name_raw, risk_level, dimensions(JSON), reviewed_at |
| `diagnoses` | AI 诊断报告 | dish_id, decision_id, summary, corrective_action, confidence, human_review_required, status |
| `sop_entries` | SOP 知识库 | dish_id, dimension, title, content, vector_id |
| `system_configs` | 系统配置（权重/推送规则等） | scope, config_key, config_value(JSON) |
| `daily_summaries` | 日报缓存 | total_reviews, positive/neutral/negative_rate, top_good/top_bad(JSON) |
| `feedback_records` | 整改效果追踪(v3.0) | decision_id, pre/post_negative_rate, improvement_pct, auto_promoted, auto_demoted |
| `chef_profiles` | 厨师画像(v3.0) | avg_positive_rate, improvement_rate, known_weak_dimensions |

- 使用 **双引擎**：`AsyncSessionLocal`（aiomysql，供 FastAPI 异步路径）+ `SyncSessionLocal`（pymysql，供 Celery 同步任务）。
- `reviews.dimensions` 存 `[{"dimension":"口味","keyword":"太咸"}, ...]` 结构。

## 4. 核心运行流程

### 4.1 数据导入 → 分析 → 沉淀（主链路）

```
用户上传 CSV/Excel（前端两段式：预览 → 勾选 → 确认）
        │
        ▼
① POST /api/v1/upload/preview
   ETLService.preview_file()
   ├─ 编码检测：utf-8-sig → utf-8 → gb18030 → gbk → chardet 兜底
   ├─ 分隔符嗅探：\t , | ;
   ├─ 列名映射：英文(raw_text/dish_name_raw...) + 中文别名(评价内容/菜品名称...)
   └─ 返回 {header, rows, total, errors} 供前端预览
        │ 用户勾选行 → 确认
        ▼
② POST /api/v1/upload/confirm
   ETLService.import_selected()
   └─ 选中行 → Review 对象 → db.flush() 写入 reviews 表
        │
        ▼
③ process_new_reviews()（同步预处理，让数据立即可见）
   ├─ 情感分析：正/负关键词计数 → positive/negative/neutral
   ├─ 维度提取：口味/卫生/分量/温度/口感/价格/服务/安全 8 维关键词匹配
   ├─ 风险评分：安全/卫生=5，口感/口味=3，紧急词(中毒/过敏/拉肚子...)=5
   ├─ 菜品匹配：Dish.name 精确匹配 → 子串包含匹配
   └─ 高风险评价 → 立即推送告警（食安级别）
        │
        ▼
④ get_dish_review_groups() 按 dish_id 聚合评价
        │
        ▼
⑤ push_dish_batch() → Redis List（key: agent:dish:queue:{batch_id}）
   process_dish_batch.delay(batch_id) → RabbitMQ 下发 Celery
        │
        ▼  ═══════ Celery Worker 异步消费 ═══════
⑥ consumer.process_dish_batch()
   while 循环：pop_dish(batch_id) → POST Agent /agent/analyze_dish
   ├─ 失败重试 3 次（间隔 5s）
   └─ 成功 → 回写 diagnoses 表（summary + corrective_action + confidence）
        │
        ▼
⑦ Agent 内部 4 节点流水线（详见 §5.1）
   ├─ 生成【一句话摘要】+【改进建议】
   ├─ 幻觉检测 → 追加警告
   └─ 异步写回 Milvus standard_collection（经验沉淀）
```

### 4.3 智能问答（ReAct 检索对话）

```
用户提问（前端 SmartChat）
   │
   ▼
Backend /api/v1/chat/query —— SSE 透传
   │
   ▼
Agent /agent/chat —— ReAct 引擎
   ├─ 创建/取会话记忆 MemoryManager
   ├─ 初始化 ReActEngine(max_iterations=5, min_confidence=0.5)
   └─ Think → Act → Observe 循环：
         LLM 决定调用哪个工具 → 执行 → 观察结果 → 再思考

        │

        │            check_fact / similar_cases ...（详见 §6.1）
        ├─ 幻觉检测（hallucination.py）
        └─ 记忆沉淀：长期记忆写回 Milvus standard_collection
   │
   ▼
SSE 流式返回（含工具调用记录 + 来源 + 置信度 + 幻觉风险）
```

### 4.4 金标飞升（人工认证）

```
品控经理在首页摘要表点赞 / 修改后确认
   │
   ▼
Backend /api/v1/config/promote（透传）
   │
   ▼
Agent /agent/promote
   ├─ 从 standard_collection 按 decision_id 精确查询
   ├─ （可选）人工修改内容后重新向量化
   ├─ 写入 gold_collection
   └─ 从 standard_collection 删除原记录

效果：被飞升的经验在后续 RAG 检索中权重 0.7（金标），优先推荐给 LLM。
```

### 4.5 自进化闭环（自动飞升/降级）

```
Celery Beat 每天执行一次 track_feedback_effectiveness
   │
   ▼
FeedbackTracker.track_all_active_diagnoses()
   对最近 30 天内已下发的 diagnosis：
   ├─ 计算整改前 7 天差评率
   ├─ 计算整改后 3/7/14 天差评率
   ├─ 改善 ≥ 10 个百分点 → 自动调用 /agent/promote 飞升金标
   ├─ 差评率上升 > 5 个百分点 → 标记失效（降级）
   └─ 写入 feedback_records 表
```

## 5. Agent 智能层详解

### 5.1 活跃的 4 节点线性流水线（`workflow.py`）

`/agent/analyze_dish` 实际运行的是这条 LangGraph 流水线：

```
entity_extraction → keyword_aggregation → rag_reranked → llm_fusion → END
```

| 节点 | 文件 | 职责 |
|------|------|------|
| ① entity_extraction | nodes/entity_extraction.py | 逐条评价 LLM NER：提取 dish/issue/process/event_type/severity/is_preference；每 15 条一批；LLM 失败降级到关键词词典 |
| ② keyword_aggregation | nodes/keyword_aggregation.py | 统计情感分布 + 维度按「权重×频次」排序，生成 keyword_summary |
| ③ rag_reranked | nodes/rag_reranked.py | 双库检索（gold k=3 ×0.7 + standard k=3 ×0.3）→ 加权合并排序 |
| ④ llm_fusion | nodes/llm_fusion.py | 组装 Prompt → LLM 生成【一句话摘要】+【改进建议】；敏感词兜底强制人工复核 |

> `llm_fusion` 输出的 `summary`/`detail` 通过正则从 `【一句话摘要】`/`【改进建议】` 标记中切分。

### 5.2 工具系统（8 个工具）

`tools/__init__.py` 启动时通过 `register_all_tools()` 注册，供 ReAct 引擎调用：

| 工具类 | 文件 | 用途 |
|--------|------|------|
| KnowledgeBaseSearchTool | kb_search.py | 向量库检索（`search_knowledge_base`） |
| DishInfoTool | dish_info.py | 查询菜品基础信息（`get_dish_info`） |
| SOPLookupTool | sop_lookup.py | 查询 SOP 标准工艺（`lookup_sop`） |
| EntityExtractionTool | entity_extract.py | 从文本提取实体 |
| FactCheckTool | fact_check.py | 事实/数字参数核查（`check_fact`） |
| SimilarCasesTool | similar_cases.py | 查找相似历史案例 |
| ConfidenceCalcTool | confidence_calc.py | 置信度计算 |
| OutputValidatorTool | output_validator.py | 输出格式校验 |

每个工具遵循统一契约（`BaseTool`）：`name` / `description` / `parameters`(JSON Schema) / `execute()` / `validate_result()` / `fallback()`，返回统一 `ToolResult{success, data, source, confidence}`。

### 5.3 ReAct 循环引擎（`react/engine.py`）

```
Think → Act → Observe → Think → ... → FINAL_ANSWER
```

- 用正则解析 LLM 输出的 `ACTION: name` + `ACTION_INPUT: {...}` / `FINAL_ANSWER: ...`。
- 自适应终止：调 `check_fact` 且置信度 ≥0.7 时提前退出；达到 5 轮上限则强制合成兜底答案。
- 置信度估算：工具调用越多 + 有事实核查/知识库检索 → 置信度越高。
- 完成后把「问题-答案」摘要作为 episode 写入长期记忆（Milvus）。

### 5.4 三层记忆系统（`memory/manager.py`）

| 层 | 实现 | 说明 |
|----|------|------|
| 短期记忆 | `deque(maxlen=20)` 滑动窗口 | 最近 20 条消息 |
| 工作记忆 | `working_context` dict | 当前分析上下文 |
| 长期记忆 | Milvus `standard_collection` | 对话摘要向量化沉淀，检索 top-k 注入上下文 |

- 压缩策略：每 10 轮或估算 token 超 3000 时，把窗口前半压缩为摘要块，提取关键事实（规则提取，不额外调 LLM）。
- 会话池全局单例，超 1 小时无活动自动清理。

### 5.5 幻觉检测（`utils/hallucination.py`）

对 LLM 输出做 6 类规则检测：绝对化表述 / 模糊表述 / 无来源数字参数 / SOP 一致性矛盾 / 来源引用缺失 / 内部矛盾（增减矛盾等）。输出 `HallucinationReport{risk_level: low|medium|high|critical}`，内置红烧肉/麻婆豆腐的已知 SOP 参数做一致性比对。

### 5.6 五维知识库（`utils/multi_kb_retriever.py`，v3.0）

| Collection | 权重 | 内容 |
|------------|------|------|
| sop_collection | 0.30 | 标准工艺 |
| pattern_collection | 0.25 | 问题→根因→方案映射 |
| cycle_collection | 0.10 | 周期规律 |
| gold_collection | 0.25 | 金标经验 |
| standard_collection | 0.10 | 普通经验 |

`multi_kb_search()` 五库并行检索 → 加权重排 → 返回 top-k。**注意**：该五库检索目前只被 `retriever` Agent（未接线的 supervisor 模式）调用；活跃的 `rag_reranked` 仍用双库（gold+standard）。

## 7. 关键架构观察（重要）

### 7.1 实现了但「未接线」的 v3.0 高级特性

代码里存在一套完整的 Supervisor 多智能体 + 信号融合 + 置信度评估，但**当前运行的线性流水线并未使用它们**：

- `workflow.py` 的 `build_supervisor_workflow()` 目前**只是 `return build_workflow()`**（注释明确写着「暂用线性模式」）。
- 活跃流水线用的是 `nodes/keyword_aggregation.py`（简单加权计数），**不是** `nodes/signal_fusion.py`（三维信号融合 + 冲突检测）。
- `nodes/confidence.py`（五因子置信度）不在活跃流水线里，因此 `/agent/analyze_dish` 中 `confidence_score`/`confidence_action` 实际是**默认值**（0.5 / publish_with_review），`conflict_analysis` 恒为「未检测到冲突信号」。
- `agents/` 六个 Agent 文件齐全，但都是「包装层」，且未被任何活跃入口引用。

> 结论：v3.0 的「信号融合 / 冲突检测 / 置信度评估 / 五库检索 / Supervisor 路由」能力**代码已写好，但尚未接入主链路**。若要启用，需把 `build_workflow()` 换成 supervisor 条件路由图。

### 7.2 多套 LLM 配置并存的隐患

`agent/config.py` 与 `backend/config.py` 各自独立加载 `../.env`，LLM/Embedding 相关默认值存在不一致（README 写 DashScope，代码默认 OpenAI）。两处 `env_file = "../.env"` 的相对路径依赖启动目录，需注意。

### 7.3 死代码：`backend/app/agent/`

`backend/app/agent/` 是**旧版内嵌 Agent**（老 3 节点 keyword/rag/llm 流水线）的完整拷贝。经查证：

- 它内部文件相互 import（`app.agent.*`），但 **backend 主入口 `main.py` 及任何活跃模块都不 import `app.agent`**。
- Backend 对 Agent 的调用已全部改为 HTTP 调 `agent/` 独立微服务（`AGENT_INTERNAL_URL`）。
- 因此 `backend/app/agent/` 是**死代码**，可安全删除（或明确归档）。

### 7.4 未完成的 TODO

- `periodic_tasks.sync_sop_to_milvus`：SOP → Milvus 同步是占位符，未实现。
- `periodic_tasks.cleanup_old_data`：空实现。
- `report_templates.py` 未接线；`ChefProfile`（厨师画像）模型已建但无写入逻辑。

### 7.5 Windows 运行注意

- Celery Worker 必须 `--pool=solo`（Windows 不支持 prefork）。
- 远程基础设施（MySQL/Redis/RabbitMQ/Milvus）默认指向 `192.168.10.20`，需按 `.env` 调整。

## 8. 快速启动

```powershell
# 1) 基础设施
docker-compose up -d            # MySQL/Redis/RabbitMQ/Milvus/etcd/minio

# 2) 初始化 Milvus 五库（仅一次）
cd agent
python init_milvus.py

# 3) Backend（终端1）
cd backend
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# 4) Agent 微服务（终端2）
cd agent
uvicorn app.main:app --host 0.0.0.0 --port 8001 --reload

# 5) Celery Worker（终端3，Windows 加 --pool=solo）
cd backend
celery -A app.tasks.celery_app worker --loglevel=info --pool=solo

# 6) Celery Beat（可选，日报/效果追踪定时任务）
celery -A app.tasks.celery_app beat --loglevel=info

# 7) 前端（终端4）
cd frontend
npm install
npm run dev                     # http://localhost:3000
```

## 9. 一句话总结

系统是一个「评价采集 → 预处理 → 多节点 LLM 诊断 → 经验向量沉淀 → 效果追踪自动进化」的品控闭环。
当前**真正跑通**的是：4 节点线性诊断流水线 + ReAct 智能问答（工具 + 记忆 + 幻觉防护）+ Celery/Redis 异步分发
+ 双库 RAG + 金标飞升。而 Supervisor 多智能体、信号融合、置信度评估、五库检索这些 v3.0 能力已编码但**尚未启用**，属于下一步接线的方向。
