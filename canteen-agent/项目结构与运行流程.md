# 食堂品控智能 Agent 系统 — 项目结构与运行流程

> 本文档按 **v4.1 实际代码**校准（含本轮清理：删除 Celery/RabbitMQ、手工 SQL 建表脚本
> 与无引用模块）。若与 README 冲突，以本文档 + 代码为准。

---

## 1. 总览

一个基于 **LangGraph + Milvus + LLM** 的菜品质量智能分析平台：自动聚合顾客评价 →
多智能体（Supervisor-Worker）诊断 → 生成整改单 → 向量库沉淀经验 → 效果追踪自动飞升金标。

### 1.1 技术栈

| 层次 | 技术 |
|------|------|
| 前端 | Vue 3 + Element Plus + ECharts + Pinia + Vite（:3000） |
| 主后端 | FastAPI + SQLAlchemy(async) + APScheduler 内嵌定时任务（:8000） |
| Agent 微服务 | FastAPI + LangGraph + LangChain + pymilvus（:8001） |
| 分析消费者 | 独立进程 `python -m app.consumer`（Redis Stream 消费组，多开即并发） |
| LLM / Embedding | OpenAI 兼容接口（默认 `gpt-4o` / `text-embedding-3-small`） |
| 消息队列 | **Redis Stream**（没有 RabbitMQ / Celery） |
| 业务库 | MySQL 8.0 |
| 向量库 | Milvus 2.4+（5 集合：sop / pattern / cycle / gold / standard） |

### 1.2 部署拓扑

```
┌──────────────┐      ┌───────────────┐      ┌────────────────┐
│  Frontend     │─────▶│  Backend       │─────▶│  Agent 微服务    │
│  Vue :3000    │      │  FastAPI :8000 │      │  FastAPI :8001  │
└──────────────┘      └──┬─────────┬──┘      └───┬────────────┘
                         │         │             │
                  ┌──────▼──┐  ┌───▼───────┐  ┌──▼────────┐
                  │ MySQL   │  │ Redis     │  │  Milvus    │
                  │ 业务数据 │  │ Stream+锁 │  │  五库向量  │
                  └─────────┘  └────┬──────┘  └────┬───────┘
                                    │              │
                            ┌───────▼──────────────▼────┐
                            │ agent-consumer（1~N 个）   │
                            │ 分片分析 → 菜品级合并 → 回调 │
                            └───────────────────────────┘
```

- Backend 通过 `AGENT_INTERNAL_URL`（默认 `http://agent:8001`）调 Agent 的问答与飞升接口。
- Consumer 通过 `BACKEND_INTERNAL_URL`（默认 `http://backend:8000`）回调写库 —— Agent 不直连 MySQL。
- 定时任务（日报 / 效果追踪 / 自动同步 / SOP 同步 / 清理）跑在 backend 进程内。

## 3. 数据模型（MySQL）

| 表 | 用途 | 关键列 |
|----|------|--------|
| `shops` / `dishes` | 店铺 / 菜品主数据 | `dishes.shop_id` 关联店铺 |
| `reviews` | 用户评价 | `synced_at`（NULL=待同步，自动同步的待办标记）、`sentiment`、`dimensions`、`risk_level`、`label_source`(dict/llm)、`dimension_detail` |
| `diagnoses` | AI 诊断报告 | `decision_id`（Milvus 关联键）、`summary`/`corrective_action`、`confidence`、`conflict_type`、`conflict_analysis`(诊断轨迹)、`human_review_required`、`status` |
| `sop_entries` | SOP 知识 | `vector_id` |
| `system_configs` | 系统配置 | `keyword_weights`、`push_rules`、`sensitive_words`、`rag_params`、`ai_inference` |
| `daily_summaries` | 日报缓存 | `top_good` / `top_bad` |
| `feedback_records` | 整改效果追踪 | `pre/post_negative_rate_*`、`improvement_pct`、`auto_promoted/demoted` |
| `chef_profiles` | 厨师画像（模型已建，待接线） | — |

> ⚠️ 枚举列由 ORM 的 `SAEnum` 写入，存的是**枚举名（大写）**：
> `POSITIVE/NEGATIVE/NEUTRAL`、`PENDING/COMPLETED/DISPATCHED/REJECTED`、
> `EXECUTED/IGNORED/EFFECTIVE/INEFFECTIVE`。手工 SQL 写入时必须用大写，否则 ORM 查不到。

数据库只由 `backend/init_db.py` 初始化（`Base.metadata.create_all` + 幂等种子），
**不再维护手工建表 SQL**；增量变更走 Alembic（`backend/migrations/`）。

## 4. 运行流程

### 4.1 主链路（评论 → 诊断）

```
评论进入 reviews 表（外部系统写入 / SQL 导入；本项目不提供上传接口）
   │
   ├─ ① 自动同步：APScheduler 每 AUTO_SYNC_INTERVAL_MINUTES（默认 5）分钟
   │      也可手动 POST /api/v1/sync（前端 AgentConfig 页按钮）
   │      取 synced_at IS NULL AND is_valid=1
   ├─ ② 预处理（词典，services/review_processor.py）
   │      情感：加权词典 + 否定翻转 + 平局偏负面
   │      维度：8 维关键词 → [{"dimension","keyword"}]
   │      风险：安全/卫生=5，口感/口味=3，紧急词=5 → risk_level≥5 立即 CRITICAL 告警
   │      菜品匹配：dishes.name 精确 → 去空格包含
   │      label_source='dict'（召回提示，不是结论）
   ├─ ③ 按菜品聚组 → 每片 80 条 → XADD agent:dish:stream（按最高风险降序）
   └─ ④ 入队成功后标记 synced_at 并提交（失败不标记，下次重试）
         │
         └─ agent-consumer 消费（消费组 analysis-group）
              ├─ 分片级：extractor(NER) → facts；结果 RPUSH + INCR 计数
              └─ 最后一片 → run_dish_analysis（菜品级）
                    merge_facts → supervisor_workflow（LangGraph 星形图）
         │
         └─ 回调 POST /api/v1/internal/diagnosis
              ├─ 幂等：decision_id 已存在直接返回
              ├─ 写 diagnoses（含诊断轨迹）
              ├─ 回写评论精判：sentiment/dimensions/risk_level/dimension_detail，label_source='llm'
              └─ human_review_required → WARNING 告警
```

### 4.2 菜品级：Supervisor-Worker 编排

```
                    ┌──────────────┐
        ┌──────────▶│  supervisor  │◀──────────┐
        │           └──────┬───────┘           │
        │                  │ 条件边            │ 所有 Worker 干完都回中枢
        │      ┌───────────┴───────────┐       │
        │      ▼           ▼           ▼       │
   extractor       analyst        auditor ─────┘
   retriever       prescriber     reporter
        │
        └─ next_worker == FINISH → END
```

- **两段式审核**：`audit` 审分析结论（事实支撑 / 食安是否触发整改）；`report_audit` 审
  真正要交付的整改单（幻觉、绝对化表述、正文过短、步骤不足），带 `revision` 版本号，
  整改单重写后旧审核自动过期、必须重审。
- **护栏**：依赖顺序校验（跳步会被回退到确定性链路）、Worker 调用额度
  （auditor 3 次，其余 2 次）、`MAX_STEPS` 轮数上限、`FINISH` 必须先有 `report_ok`。
- **打回**：只有 `prescriber` 会被打回（它调 LLM，换个指令真能改写）；分析节点是
  确定性节点，重跑必然同结果，所以预审不过只标人工复核、不打回。

### 4.3 定时任务（APScheduler，内嵌 backend 进程）

| 任务 | 周期 | 说明 |
|------|------|------|
| `auto_sync_new_reviews` | 5 分钟（可配，0=关） | 未同步评论 → 预处理 → 分片入队 |
| `generate_daily_summary` | 1 小时 | 好评/中性/差评率 + 红黑榜 TOP3 → `daily_summaries` |
| `track_feedback_effectiveness` | 24 小时 | 3/7/14 天观察窗；有效→自动飞升金标，失效→标记 ineffective |
| `sync_sop_to_milvus` | 12 小时 | 未实现（TODO） |
| `cleanup_old_data` | 24 小时 | 未实现（TODO） |

> 任务跑在 backend 进程里：多副本部署会重复执行，请保持单副本或把定时任务集中到一个实例。

### 4.4 智能问答

```
前端 /chat → Backend /api/v1/chat/query（SSE 透传） → Agent /agent/chat
   → ReActEngine（原生 function calling，最多 5 轮）
        工具：search_knowledge_base / lookup_sop / get_dish_info / check_fact /
              similar_cases / calc_confidence / validate_output / extract_entities
   → 幻觉检测 + 置信度标注 + 记忆沉淀（Milvus standard）
```

### 4.5 告警推送

```
触发点：
  ├─ 预处理：risk_level ≥ 5 → CRITICAL
  └─ 回调落库：human_review_required → WARNING
        │
        ▼
PushDispatcher.dispatch(alert, db)   ← 必须传 db 才会读 system_configs.push_rules
  ├─ 默认规则：CRITICAL→[企业微信,钉钉]；WARNING/INFO→[企业微信]
  └─ 通道：WechatWorkPusher / DingTalkPusher(加签) / EmailPusher(SMTP)
```

## 7. 快速启动

```bash
# 1) 基础设施
docker compose up -d

# 2) 建库 + 建表 + 种子数据（幂等）
cd backend && python init_db.py

# 3) Milvus 集合（仅一次）
cd ../agent && python init_milvus.py

# 4) Backend（API + 推送 + 定时任务）
cd backend && uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# 5) 分析消费者（可多开）
cd agent && python -m app.consumer --consumer c1

# 6) Agent 微服务
cd agent && uvicorn app.main:app --host 0.0.0.0 --port 8001 --reload

# 7) 前端
cd frontend && npm run dev
```

## 8. 待办与已知限制

- `sync_sop_to_milvus` / `cleanup_old_data` 仍是空实现。
- `chef_profiles`（厨师画像）模型已建，无写入逻辑。
- 评论入库没有表单/connector 入口，依赖外部系统写 MySQL（自动同步兜住后续流程）。
- `feedback_tracker` 以诊断生成时刻为观察起点（模型无 `dispatched_at` 列）；
  如需精确到「下发时刻」需加列 + Alembic 迁移。
- 多副本 backend 会重复执行定时任务。
